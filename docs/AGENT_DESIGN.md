### 충돌 방지와 인계

- 기존 Claude는 출처 리서치와 사용자가 요청한 투자 규칙/YAML 작업을 유지한다. Codex는 사용자의 후속 요청에 따라 `web/` 컨셉 화면과 실행·검수 작업을 맡는다. `tools/`, `rules/`, `docs/wiki/`는 이번 UI 작업에서 수정하지 않는다.
- Claude의 구현 담당 표시는 **수락 전 제안**이다. 해당 세션이 내용을 확인하고 담당/현재 작업을 기록하면 수락으로 바꾼다. 새 Claude 세션을 복제해 같은 작업을 시작하지 않는다.
- 같은 파일은 한 작업자만 수정한다. `CHANGELOG.md`·`DECISIONS.md` 등 공용 파일은 쓰기 직전에 다시 읽고 자신의 항목만 추가한다. 다른 세션의 수정/커밋/투자 결정을 되돌리지 않는다.
- 다른 담당 경로가 필요하면 이 절에 인계 범위와 상태를 남긴 후 수정한다. 필요할 때 독립 브랜치/작업 트리를 사용하되 동일 파일 동시 수정 문제를 숨기는 용도로 쓰지 않는다.
- 제품 진행률에 과거 체크 수를 쓰지 않는다. 디자인/실데이터/동작/검증을 따로 보고한다. 테스트 성공이나 라이브러리 변경만으로 컨셉 화면 완료를 선언하지 않는다.

## 구조 원칙
"겉으로는 Agent 하나, 안에서는 여러 역할과 도구로 분리."
- 사용자에게는 "연금 재배분 Agent" 하나로 보인다
- 내부는 메인 Agent 1개 + deterministic tools 여러 개. 멀티 에이전트는 첫 PoC에서 쓰지 않는다
- 기능이 커지면 일부 역할을 sub-agent로 승격. 단, 계산은 끝까지 코드 함수/룰 엔진 — LLM이 비중을 계산하는 구조는 신뢰성이 떨어진다
- 책임 분리: 숫자 → 코드/DB, 규칙 → wiki, 판단 조건 → deterministic logic, 설명/대화/기억 → Agent
- 스터디 관점: single-agent architecture를 먼저 이해하고, 그다음 "어디부터 sub-agent로 분리할지"를 학습

## 1. 첫 Agent 정의 (고정)
### Pension Rebalancing Agent
사용자가 정한 전략과 규칙을 기억하고, 새 잔고가 들어오면 현재 비중을 계산해 목표 비중과 비교하고, 재배분이 필요하면 매수·매도 수량을 산출하고, 왜 필요한지 설명하며, 사용자의 수락/거절을 다음 판단에 반영한다.

### 내부 역할 (PoC에서는 전부 tool, 추후 승격 후보)
| 역할 | PoC 형태 | 하는 일 | 승격 시점 |
|---|---|---|---|
| Input | tool `parse_balance` / `fetch_prices` | 캡처 이미지/CSV/시트 → 보유 내역(종목·수량·매입금액, 1회 등록) / 종목코드로 현재가 조회(공개 시세, 매번) | 입력 소스가 5개 이상, 오류 처리가 대화형이 되어야 할 때 |
| Tagging | tool `tag_assets` | 종목 → 자산군(주식·장기채·중기채·금·원자재·현금 등) + 계좌 태그(주머니/층/세제구분/레거시). 매핑표 우선, 없으면 LLM 분류 후 사용자 확인 | 신규 종목 분류 정확도가 문제될 때 |
| Strategy | tool `load_strategy` | 사용자가 선택한 전략의 목표 비율·임계치를 wiki/DB에서 로드 | (승격 불필요, 순수 조회) |
| Rebalancing Engine | tool `compute_rebalance` (순수 함수) | 현재 비중 계산, 목표와 비교, 발동 여부, 매수·매도 금액·수량 산출, 제도 제약 검증 | 절대 승격하지 않음 — 항상 코드 |
| Explanation | Agent 본체 (+ tool `explain_inputs`) | 편차·가정 하락장 손실 비교 수치를 받아 "왜 지금" 한 문단 생성 | 설명이 개인화·대화형으로 깊어질 때 |
| Action | tool `build_order_sheet` | 주문표(계좌·종목·매수/매도·수량·예상금액) 생성. 2단계에서 MCP/KIS API 실행 연결 | 자동주문 Level 1 이상 |
| Memory | tool `record_decision` / `read_decisions` | 수락/거절/사유를 DECISIONS.md(또는 DB)에 기록·조회 | — |

### 워크플로우 (한 바퀴)
0. 계좌 선택: 소유자(나/배우자) · 증권사 · 계좌 종류(연금저축/IRP/ISA/일반) + **풀**(합산할지 따로 갈지)과 풀의 **전략·모드**(리밸런싱 / 매수만). 처음 로그인 때 고르고 설정에서 바꾼다 (SCREEN_REFERENCE "계좌 묶기"). 목록은 `rules/accounts.yaml`. 모든 잔고 행은 이 세 칸을 달고 다닌다 (나중에 IRP·배우자 계좌 합산 시 구조를 안 바꾸기 위해). PoC는 설정 파일 고정, 로그인·가족 초대는 v1.5
1. 사용자: 그 계좌의 잔고 캡처 또는 CSV 투입 (+ "리밸런싱 봐줘")
2. `parse_balance` → 표
3. `tag_assets` → 자산군·계좌 태그 (미확정 항목은 사용자 확인)
4. `load_strategy` → 목표 비율·임계치·제약
5. `compute_rebalance` → 현재 비중, 편차, 발동 여부, 주문 금액·수량, 제약 검증 결과
6. 발동 시 `build_order_sheet` → 주문표 / 미발동 시 "이번엔 안 해도 됨" + 편차 현황
7. Agent: `explain_inputs` 수치로 "왜" 설명 작성, `read_decisions`로 지난 거절 사유 반영
8. 사용자 수락/거절/보류 + 사유 → `record_decision`
9. (2단계) 승인 시 KIS API 실행 → 로그

### `compute_rebalance` 출력 (화면·설명·주문표가 공유하는 데이터 계약)
목업 `docs/assets/mockup-rebalancing.html`의 각 영역이 그대로 이 구조에서 나온다. 1주차에 이 구조를 먼저 고정한다.
- `account`: 소유자·증권사·계좌종류, 잔고 기준일
- `strategy`: 전략 id·이름, 임계치, 최소 거래 금액
- `total_value`, `new_cash`(신규 납입)
- `classes[]`: 자산군별 목표 비중 t_i, 현재 비중 w_i, 편차 d_i(%p), 평가액, 발동 여부
- `triggered`: 하나라도 임계치를 넘었는지
- `constraints[]`: 제도 검증 항목(연금저축 ETF 적격, 레버리지·인버스 없음, IRP 70% 등)과 통과 여부. 하나라도 실패하면 주문표 없음 + 사유
- `orders[]`: 구분(매도/매수/생략) · 자산군 · 종목 · 수량 · 예상 금액 · 비고(편차, 납입금 포함, 생략 사유). 매도 먼저
- `explain_inputs`: L_now, L_target, 차이, 편차 최대 자산군, 과세이연 여부
- `last_decisions[]`: 같은 자산군에 대한 지난 수락/거절/보류와 사유

## 2. 이전 PoC 범위·진행 이력 — 현재 계획은 §0

아래는 기존 Streamlit PoC의 범위와 완료 기록이다. 기술·화면 우선순위·저장 단계가 §0과 다르면 §0을 적용한다. 이전 [x]는 새 React 화면·모바일·보안 검증 완료를 뜻하지 않는다.

### 목표
"잔고 캡처/CSV → 자동 태깅 → 목표비율 비교 → 주문표 생성 → 이유 설명"까지.
2026-10-26 조정: 1~2주 뒤 아이디에이션 회의를 위해 Streamlit 메인 화면(홈) + 리밸런싱 화면 한 장을 먼저 올린다. "메인 화면을 세우고 기능을 붙여 가는" 순서. Agent 본체(설명 생성·결정 기록)와 캡처 파싱은 회의 후에 붙인다.

### 포함
- 입력: 미래에셋 앱 "국내주식 잔고" 화면 캡처(비전 파싱) — CSV 내보내기가 없어 캡처가 1주차 주 경로. 샘플 캡처 6장과 손으로 옮긴 정답 CSV는 `data/samples/`(git 제외). 계좌는 본인 연금저축 (구)+(신) 2개 합산, IRP 추가는 회의 후. 키움(주식)은 현금 주머니라 PoC 밖, 한투는 2027년 계좌 개설 후 2단계
- 입력 구조 (2026-10-26 확정): 변하지 않는 것(종목·수량·매입금액)은 캡처 한 번으로 등록해 파일에 저장. 매일 변하는 것(현재가)은 공개 시세(네이버 금융/KRX, 국내 상장 ETF)에서 종목코드로 조회 → 증권사 API 불필요. 캡처 재등록은 거래·납입으로 수량이 바뀔 때만 (주문표대로 체결했다고 확인하면 코드가 수량 갱신). tool `fetch_prices` 추가
- 캡처 파싱 검증: 파싱 합계와 캡처의 총평가액을 코드로 대조하고, 불일치면 사용자가 표를 고쳐 확정한다. "오차 0"은 샘플 캡처 세트에 대한 테스트 기준
- 태깅: 자산군 매핑표(`rules/asset_map.yaml`) 우선. 미등록 종목은 LLM이 첫 분류를 제안하고 사용자가 확인하면 YAML에 저장, 이후 실행은 YAML만 읽는다 (같은 잔고 → 같은 주문표)
- 전략: 올웨더 원형 + 직접 설정 2종. K-올웨더는 사용자가 비율 채우면 추가
- 계산: 현재 비중, 편차, ±5%p 임계치 발동, 매수/매도 금액·수량(호가·정수 주 반영), 현금흐름 리밸런싱 우선안, 연금저축 제약(레버리지·인버스 불가) 검증
- 출력: 주문표(표) + "왜 지금" 설명 한 문단(가정 하락장 손실 비교 수치 포함). 회의 전까지는 코드 템플릿 문장에 수치만 끼우고, 회의 후 Agent 생성으로 교체
- 첫 테스트 시나리오: 현재 잔고 + IRP 신규 납입 300만원 → 매도 없이 매수만으로 주문표(현금흐름 리밸런싱). 올해 미납입분이라 실제로 쓸 주문표가 된다
- 계좌: `rules/accounts.yaml`에 소유자·증권사·계좌종류 목록. 로그인 없음(본인 로컬 도구). 화면 상단 "부부전체/나/배우자" 토글은 두되 배우자는 샘플 숫자
- 화면(Streamlit, `app/`): 목업의 좌측 메뉴 + 홈(두 주머니 카드, 샘플 숫자) + 리밸런싱(CSV 업로드 → 목표 vs 현재 막대 → 주문표 → 설명). 연금 메뉴는 4층 석탑 샘플 그림까지, 부동산·세금·가족은 메뉴만 "준비 중". CLI 출력도 화면과 같은 순서(전략 → 비율 → 주문표 → 설명)로 고정
- 기억: 수락/거절/사유를 DECISIONS.md에 append, 다음 실행 때 읽어서 설명에 반영
- 지식: TAX_RULES / REBALANCING_RULES / CALCULATION_RULES 마크다운을 시스템 컨텍스트로 주입 (llm-wiki)

### 제외 (2단계 이후)
- 실제 주문 실행(KIS API) — 드라이런만
- IRP 70% 한도 검증 (IRP 계좌 추가 시), ISA
- 배우자 계좌·가족 계정, 구글시트 연동, 부동산, 세금 시뮬레이션. 화면은 홈·리밸런싱 두 장만(위 포함 항목), 나머지 메뉴는 "준비 중"
- 저장소: PoC는 파일만(data/ 스냅샷 CSV, DECISIONS.md). DB(SQLite)는 v1.5

### 완료 기준 (Definition of Done)
1. 같은 CSV를 두 번 넣으면 같은 주문표가 나온다 (계산 결정성)
2. 캡처 이미지로 정답 CSV와 동일한 표가 나온다. 검사 칸은 종목명·수량·현재가 세 개 (이 셋이 주문표를 결정한다. 매입금액·손익은 참고 칸이라 검사 대상 아님)
3. 목표 비율을 바꾸면 주문표가 그에 맞게 바뀐다
4. 레버리지 ETF를 넣으면 주문표 생성이 중단되고 이유가 표시된다
5. 거절 사유를 기록한 뒤 다시 실행하면 설명에 그 사유가 언급된다
6. 설명에 예측 표현("오를 것")이 없다
