# MASTER_PRD — 제품 요구사항

최종 갱신: 2026-10-27 · 상태: 컨셉 구현·구조 전환 진행 기준
맥락은 MASTER_CONTEXT.md, 화면은 SCREEN_REFERENCE.md, Agent·PoC 범위는 AGENT_DESIGN.md

현재 실행 순서와 담당은 `AGENT_DESIGN.md` §0이 원본이다. 기존 P0/P1/P2 분류 중 아래 컨셉 홈·입력 검증·구조 전환에 해당하는 부분은 이번 우선 범위로 승격한다. 전략 비율·종목·자동주문 범위는 기존 결정대로 유지한다.

## 1. 제품 한 줄
부부가 각자의 연금과 현금 주머니를 규칙대로 굴리고, 은퇴 후 매달 얼마 받을지와 가고 싶은 집까지 얼마 모자란지를 알게 해주는 은퇴 가계 노트.
철학: "입력은 캡처 한 장, 판단은 두 분의 규칙, 제안은 에이전트가, 결정은 기록으로."

## 2. 대상·형태
- 1차: 사용자 부부가 쓰는 개인 도구 (규제 무관, 자동매매는 본인 계좌)
- 2차(검토): 계산기 형태의 서비스. 전략·종목은 사용자가 선택, 앱은 차이·수량만 계산. "추천" 표현 금지. 자동주문은 각자 자기 API 키로만

## 3. 문제 정의
- P1 규칙 기반 리밸런싱을 하고 싶지만 왜 해야 하는지 잊고, 직접 비율을 맞추기 어렵다
- P2 연금이 4층(국민·퇴직·개인·ISA)으로 흩어져 있어 결국 매달 얼마 받는지 모른다
- P3 수령 순서·세금에 따라 실수령액이 달라지는데 설계할 도구가 없다
- P4 연금 외 저축(현금 주머니)이 집 갈아타기 목표와 연결되어 있지 않다
- P5 마이데이터 없이 자산을 쉽게 입력할 방법이 없다

## 4. 기능 요구사항 (우선순위: P0 PoC / P1 v1.5 / P2 v2)
### 입력
- [P0] CSV 잔고 업로드 → 표 변환 / [P0] 캡처 이미지 → 표 변환 / [P0] 자동 태깅(자산군·주머니·층·세제구분·레거시) + 사용자 확인
- [P1] 구글시트 연동(템플릿 복사·읽기) / [P1] 계좌별 갱신일·월 1회 리마인드 / [P2] 증권사 API 잔고 자동 조회 / [P2] 대화형 입력
### 리밸런싱
- [P0] 전략 선택(올웨더/직접) → 목표 vs 현재 비중 → 발동 판단 → 주문표 / [P0] "왜 지금" 설명 / [P0] 수락·거절·사유 기록 및 다음 제안 반영 / [P0] 연금저축 제도 제약 검증
- [P1] IRP 70% 한도 검증, K-올웨더·박곰희 템플릿 / [P1] 레거시 태그·현금흐름 리밸런싱·전환 글라이드 / [P2] 승인형 자동주문(KIS API) → 완전 자동
### 연금 수령
- [P1] 4층 석탑 입력 + 가구 월 수령액 + 연도별 그래프 + 가정 슬라이더
### 세금·수령 설계
- [P2] 계좌 태그 기반 수령 순서·연도 배치 시뮬레이션, 1,500만원 기준선, 퇴직금 실제수령연차 비율, 브릿지
### 부동산
- [P2] 관심 단지·분양권 팔로우(시세·갭·실거래·뉴스), 필요 자금 역산, 시나리오 비교(실거주 vs 분양권+월세), 노후 주머니 영향
### 가족
- [P1] 초대코드 패밀리, 각자 자산 소유·합산 뷰, 편집 권한 / [P2] 자녀·부모 확장
### 홈·알림
- [P0-화면] concept.jpg 기준 네이비 메뉴·사진 머리글·총자산/두 주머니 카드·자산 도넛·은퇴 목표·전략 배분·가구 소득 차트·알림. 데스크톱과 모바일(원형 카드·하단 탭)을 고정 데모로 먼저 검수
- [P0-연결] 등록한 자산·계좌·가격 기준일을 홈과 상세 화면에 일관되게 연결. 실제 보기의 누락 데이터를 샘플 숫자로 대체하지 않음
- [P1-계산] 은퇴 시점·소득 전망은 검증된 서버 모델 연결 후 실제 기능으로 완료 처리. 데모 차트와 실제 계산을 구분
- [P1] 두 주머니 목표 대비 %, 이번 달 제안과 영속 체크리스트, 연령 트리거 알림

## 5. 비기능 요구사항
- 시각 검수: SCREEN_REFERENCE의 데스크톱/모바일 기준 통과. 제목·메뉴 렌더링 성공만으로 화면 완료 처리하지 않음
- 경계 검증: 계좌 존재/활성/권한, 저장 경로, 수량·가격·비율, 캡처 합계와 편집 후 재검증, 신규 매수 후보 제약 검사를 서비스 경계에서 수행
- 데이터 일관성: 보유·가격·전략 버전과 기준일을 고정해 제안을 재현. 수락과 실제 체결을 구분. 저장 트랜잭션·중복 제출·변경 충돌 처리
- 공유 전 보안: 서버 계좌 권한, 비밀키 분리, 비공개 업로드, AI 입력 최소화, HTTPS·세션·CSRF·백업 복구 검증. 기본 로컬 사용은 loopback 바인딩
- 계산 결정성: 같은 입력 → 같은 출력. 모든 공식은 코드 + 단위 테스트 (CALCULATION_RULES.md)
- LLM은 계산하지 않음. 설명·대화·분류 보조만
- 규칙은 마크다운 wiki로 사람이 읽고 고칠 수 있어야 함. 세법 기준일 명시
- 데이터: 숫자는 DB(이력), 결정은 기록. 증권사 API 키는 로컬 암호화 보관, 외부 전송 금지
- 자동주문 안전장치: 한도·시간·로그·실패 시 중단
- 표현 제약: 예측·추천 문구 금지("오를 것", "이 ETF가 좋다")

## 6. 성공 지표 (개인 도구 단계)

- 리밸런싱 제안을 보고 "왜"를 다시 읽지 않아도 이해됨 (사용자 주관 평가)
- 연금 수령액 숫자를 부부가 같은 값으로 알고 있음
