## 제품 철학
"입력은 캡처 한 장, 판단은 두 분의 규칙, 제안은 에이전트가, 결정은 기록으로."

책임 분리 원칙 (모든 설계의 기준):
- 숫자 → 코드/DB (LLM은 계산하지 않는다)
- 규칙 → wiki (마크다운, Agent 컨텍스트로 주입, 사람이 읽고 고칠 수 있음)
- 판단 조건 → deterministic logic (임계치·한도·제도 제약은 코드로 검증)
- 설명/대화/기억 → Agent

## 출발점과 의도
- 기존 다른 계정에서 "부부연금프로젝트"로 연금 기반 월렛을 기획. 서비스명 시안 둘이서은퇴(RetireTogether). 컨셉 이미지는 SCREEN_REFERENCE.md
- 사용자 경험: 연금계좌 수익률은 좋았고 일반 주식계좌는 나빴음 → 차이는 "규칙의 유무". 40대 진입. 『마법의 연금굴리기』를 계기로 연금저축을 연금펀드로 이전, 박곰희 등 저자 책을 읽고 규칙 기반 자산배분(올웨더, K-올웨더 등)을 하고 싶어짐
- 문제 1: 리밸런싱을 왜 해야 하는지 당위성이 자꾸 잊힘 → "왜"를 숫자로 계속 상기시키는 것 자체가 기능
- 문제 2: 직접 비율 맞추기가 어려움 → 규칙대로 주문표를 만들고, 본인 계좌는 API로 자동화

## 자산 구조: 두 개의 주머니 (확정)
- 노후 주머니 = 연금. 완전히 분리. 4층 석탑(국민연금 / 퇴직연금 DB·DC·IRP / 개인연금 연금저축펀드·세제비적격 연금보험 / ISA→만기 후 연금계좌 이전). 55세 이후를 위한 돈. "비율 유지" 리밸런싱
- 현금 주머니 = 연금 외 각자 저축액 = 주식 + 현금. 부동산 갈아타기의 재원. "목표일에 맞춘 글라이드"
- 부동산은 주머니가 아니라 "지금 집"과 "가고 싶은 집" 두 지점. 필요 자금 = 목표 집 가격(+취득세·중개비) − (현재 집 매도 예상액 − 대출 잔액) − 현금 주머니 → "월 얼마/몇 년" 역산
- 부부 각자 + 합산. 연금 납입 ↔ 현금 주머니 목표 사이 트레이드오프가 부부 의사결정 화면의 핵심
- 최종 산출물: "우리 집 예상 월 연금 실수령액"(노후) + "저 집까지 얼마 모자라나"(현금)

## 기존 보유분(레거시) 처리
- 현금 주머니의 기존 개별 종목은 "레거시" 태그로 리밸런싱 계산에서 분리. 신규 납입·배당만 규칙대로(현금흐름 리밸런싱). 레거시는 수년에 걸친 전환 글라이드 + 손익통산 타이밍 제안
- 연금계좌는 과세이연이라 바로 규칙 적용

## 계좌 현황 (2026-10-26)
- 연금저축: 미래에셋 (구)+(신) 두 계좌, 리밸런싱은 합산 기준·주문은 계좌별. 2026-10-26 캡처 기준 평가 약 2,350만 + 3,900만. 연금계좌 API 조회 지원 여부 미확인(아래 미결) → 당분간 앱 캡처가 입력 경로, 주문은 수동
- IRP: 증권사 미확인 (미래에셋으로 가정). 올해 300만원 미납입 → 첫 테스트 시나리오
- 주식(현금 주머니): 키움. PoC 범위 밖
- 2027년부터 신규 연금펀드 납입은 한국투자증권 → 자동주문(2단계) 대상 계좌

## 자동매매 (본인 계좌 한정)
- API 키는 개인 단위 → 부부 각자 계좌·각자 키. 본인 계좌 자동화는 투자일임 아님
- 한국투자증권 KIS API: 연금저축(상품코드 22)·IRP(29)는 일반 주문 TR에 코드만 바꾸는 구조. 조회 API는 문서화, 주문 수용 여부는 실계좌 소액 테스트로 확인(모의투자 불가). 퇴직연금 잔고조회는 펀드 미포함. DC 불가. ISA 미확인(안 되면 수동 주문 폴백). 타 증권사 연금 API 근거 없음
- 제도 제약을 코드로 사전 검증: 연금저축은 국내 상장 ETF만(레버리지·인버스 불가), IRP 위험자산 70% 한도 (REBALANCING_RULES.md)
- 단계: 드라이런 → 승인형(human-in-the-loop) → 완전 자동. 한도·임계치·로그 필수. 자동매매는 PoC 2단계

## 입력 (마이데이터 없이)
- 마이데이터는 허가 사업자만 → 직접 연동 불가. 입력 장벽을 낮추는 게 경쟁력
- 경로: 증권사 API(본인 계좌) / 구글시트 연동(템플릿 복사, 데이터는 사용자 구글에 남음) / 엑셀·CSV 업로드 / 캡처 붙여넣기(비전으로 표 변환 — API 안 되는 계좌의 주 경로) / 대화형 입력 / 직접 편집
- 변하지 않는 것(종목·수량·매입금액)은 한 번 등록, 변하는 것(현재가)은 공개 시세로 매번 조회. 캡처는 처음과 거래 후에만 → 입력 장벽이 "매달 캡처"에서 "처음 한 번"으로
- 처음엔 계좌 단위 총액만으로 대시보드가 뜨고, 종목 단위는 리밸런싱 때 추가. 월 1회 갱신 리마인드
- 자동 태깅: 종목·계좌명 → 주머니, 4층 중 몇 층, 세제적격/비적격/퇴직금 원천, 레거시 여부. 사용자는 확인만

## 가족 계정
- 한 명 가입 → 초대코드(1회용·유효기간) → 배우자 가입 시 같은 패밀리(=가구). 각자 자산은 본인 소유, 합산 뷰 공유, 상대 자산 편집 권한은 설정. 자녀·부모 확장 가능. 로그인은 구글 우선(시트 권한 동시 획득)

## 부동산
- 관심 단지·분양권 팔로우 카드: 매매·전세가·갭·실거래·뉴스·분양 일정. 시나리오 비교(실거주 갈아타기 vs 분양권 보유+월세)를 연도별 현금흐름과 현금 주머니 목표 시점, 노후 주머니 영향으로. 데이터: 국토부 실거래가 API, KB/부동산원 시세, 청약홈, 뉴스 검색

## 세금·수령 설계 (상세는 TAX_RULES.md, 기준일 2026-10-26)
- 사적연금 연 1,500만원은 "절벽"이 아니라 시뮬레이션 기준선(이하 분리과세 선택, 초과 시 종합과세 또는 16.5% 분리과세 선택). 부부 각자 한도
- 퇴직금 연금수령은 연금실제수령연차 기준 10년 이하 70% / 10~20년 60% / 20년 초과 50% 과세. "55세 즉시 개시가 항상 유리"를 하드코딩하지 않고 시나리오로 비교
- 세제비적격 연금보험은 비과세 요건 충족 시 한도 밖 → 브릿지·초과분 용도
- 55세 사적연금 vs 국민연금 개시 사이 브릿지 설계

## 규제 경계
- 투자자문업 기준은 주체가 아니라 "영업으로 투자판단 제공"인지. 개인 도구는 무관. 서비스화 시 ① 계산기로 선 긋기(사용자가 전략·종목 선택, "추천" 문구 금지) ② 등록 자문·일임업자 제휴 ③ 직접 등록. 타인 계좌 자동매매는 투자일임 → 불가. 한화 그룹 내 라이선스 활용 가능성

## 지식·데이터 저장 (3층)
- 숫자(잔고·납입·목표·주문 로그) → DB, 이력 포함
- 규칙·지식(세법·제도 제약·전략 정의·책에서 배운 원칙·부부의 결정) → llm-wiki (docs/*_RULES.md, DECISIONS.md). 큐레이터 Agent가 갱신
- 외부 문서 스트림(단지 뉴스·공시) → RAG. 양이 많고 쌓이는 것만

## 개발 방향
- 목적: 사용자 본인이 Claude로 개발하며 AI Agent 역량 강화
- UI는 "화면 = 질문 하나" 수준까지만 기획(SCREEN_REFERENCE.md). 로직(순수 함수)부터 만들되, 1~2주 뒤 아이디에이션 회의를 위해 Streamlit 메인 화면(홈)+리밸런싱 화면을 먼저 올린다 (AGENT_DESIGN §2 일정). FastAPI는 화면·백엔드를 분리할 때 후보
- 스택: Claude Code + uv(Python 3.12) + Claude Agent SDK(Python) + Streamlit + MCP(KIS API 래퍼 등). 필요 시 LangGraph. LLM 실행 엔진은 Claude, 개발 중 GPT는 브레인스토밍 보조. Task Master를 쓸 경우 PRD 입력은 AGENT_DESIGN §2(PoC 1페이지)만
- 첫 Agent: Pension Rebalancing Agent (AGENT_DESIGN.md의 PoC 1페이지)
